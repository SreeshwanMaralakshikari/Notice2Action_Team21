# Notice2Action — Backend

A REST API that receives a notice — pasted text or a PDF upload — sends it to Google Gemini, and returns a structured JSON with a summary, deadlines, eligibility conditions, and a step-by-step checklist. Results are saved to MongoDB so the frontend can fetch them by ID and persist checklist state across sessions.

---

## What This Project Does

A user submits a notice through the frontend. The backend extracts the text (from a PDF if needed), constructs a prompt that asks Gemini to analyze the notice and return a fixed JSON structure, strips any markdown wrapping from the response, parses the JSON, saves the result to MongoDB, and returns the full document to the frontend. Subsequent requests from the frontend — fetching results by ID or updating a checklist item — hit lightweight database endpoints with no AI involved.

## Tech Stack

- Node.js with CommonJS modules
- Express 5
- MongoDB with Mongoose 9
- Multer 2 for multipart file handling (memory storage)
- pdf-parse for PDF text extraction
- Google Generative AI SDK for Gemini API access
- dotenv for environment configuration

## Environment Variables

```
PORT=5000
DB_URL=mongodb://localhost:27017/notice2action
GEMINI_API_KEY=your_key_from_google_ai_studio
FRONTEND_URL=http://localhost:5173
```

`PORT` — the port Express listens on. Defaults to 5000.

`DB_URL` — MongoDB connection string. Use `mongodb://localhost:27017/notice2action` for local development or your Atlas connection string in production.

`GEMINI_API_KEY` — your key from [Google AI Studio](https://aistudio.google.com). Free tier, no credit card required. The `gemini-3.6-flash` model is used.

`FRONTEND_URL` — used to configure CORS. In production, set this to your exact Vercel deployment URL including the protocol and without a trailing slash. A missing value is handled safely — the CORS origin list is built with `filter(Boolean)` so `undefined` is never added as an allowed origin.

Never commit `.env` to git — it is already in `.gitignore`.

## Schema and Model

### NoticeModel

```
summary         String      required — plain-language overview generated by Gemini
deadlines       [Object]    array of { label: String, date: String } pairs
eligibility     [String]    array of eligibility condition strings
checklist       [Object]    array of { task: String, done: Boolean }
category        String      notice type — Fee, Exam, Scholarship, Hostel, Event, General, etc.
createdAt       Date        auto-set by Mongoose timestamps: true
updatedAt       Date        updated whenever a checklist item is ticked or unticked
```

Deadlines are stored as `{ label, date }` string pairs rather than JavaScript `Date` objects. This avoids parsing failures when Gemini returns natural-language date strings like "last working day of the month" that cannot be reliably converted to a `Date`.

## API Endpoints

All routes are mounted under `/notice-api` in `server.js`.

### Notice Routes — /notice-api

| Method | Endpoint | Description |
|--------|----------|-------------|
| POST | `/notice-api/process` | Process a notice. Accepts pasted text as JSON (`{ "text": "..." }`) or a PDF file as multipart form data (`file`). Runs the full AI pipeline and returns the saved notice object including its `_id`. |
| GET | `/notice-api/notice/:id` | Fetch a previously processed notice by its MongoDB `_id`. The frontend uses this when navigating to Results or Checklist from the Recent strip. |
| PUT | `/notice-api/notice/:id/checklist` | Update the `done` field on a single checklist item. Body: `{ "index": 2, "done": true }`. Called every time a user ticks or unticks a step. |

---

### POST /notice-api/process — Request Formats

**Pasted text:**
```
Content-Type: application/json

{ "text": "...the full notice content..." }
```

**PDF upload:**
```
Content-Type: multipart/form-data

file: <pdf file>
```

**Response (both formats):**
```json
{
  "_id": "64f2a...",
  "summary": "The college has announced a fee payment deadline...",
  "deadlines": [
    { "label": "Fee payment deadline", "date": "30 Aug 2026" }
  ],
  "eligibility": [
    "3rd year B.Tech students",
    "All branches"
  ],
  "checklist": [
    { "task": "Download the fee challan from the student portal", "done": false },
    { "task": "Pay the fee at the designated bank counter", "done": false },
    { "task": "Upload the payment receipt to the portal", "done": false }
  ],
  "category": "Fee",
  "createdAt": "2026-08-27T10:00:00.000Z",
  "updatedAt": "2026-08-27T10:00:00.000Z"
}
```

---

### PUT /notice-api/notice/:id/checklist — Request Format

```json
{ "index": 0, "done": true }
```

`index` is the zero-based position of the checklist item in the array. `done` is the new boolean state. The handler uses MongoDB's `$set` with a computed field path (`checklist.0.done`) to update only that element without rewriting the whole array.

## How the AI Pipeline Works

### Step 1 — Text extraction
If the request is multipart, Multer captures the uploaded file in memory (no disk writes). `extractPdfText.js` passes the buffer to `pdf-parse`, which extracts the raw text content. If the request is JSON, the text is used directly.

### Step 2 — Prompt construction
`buildNoticePrompt.js` wraps the notice text in a prompt that instructs Gemini to:
- Read the notice carefully
- Return a JSON object with exactly five fields: `summary`, `deadlines`, `eligibility`, `checklist`, `category`
- Use the specific structure for each field (the schema is spelled out explicitly)
- Never include any text outside the JSON object

Specifying the schema in the prompt is what makes the response reliably parseable without a validation layer.

### Step 3 — Gemini call
`gemini.js` initialises the Google Generative AI SDK with the API key and exports a configured `model` object. `NoticeAPI.js` calls `model.generateContent(prompt)` and reads `response.text()`.

### Step 4 — Response parsing
Gemini occasionally wraps its JSON in markdown code fences (triple backticks). A regex strips any leading ` ```json ` or ` ``` ` and trailing ` ``` ` before calling `JSON.parse`. If parsing fails, a 500 error is returned with the raw response for debugging.

### Step 5 — Save and respond
The parsed object is saved as a `NoticeModel` document with `{ timestamps: true }`. The full saved document (including its MongoDB `_id`) is returned as JSON with status 201.

## Utility Functions

### extractPdfText.js
Wraps `pdf-parse`. Accepts a file buffer (from Multer memory storage) and returns the extracted text string. Throws on corrupt or encrypted PDFs — the error propagates to the route handler which returns 400.

### buildNoticePrompt.js
Builds the Gemini prompt string. Takes the notice text as input, returns the full prompt with the schema specification embedded. Keeping the prompt in its own file makes it easy to iterate on without touching the route handler.

## Key Design Decisions

- **Memory storage for Multer** — files are kept in RAM and passed directly to `pdf-parse` as a buffer. No temp files are written to disk. This is appropriate for the file sizes involved (notice PDFs are typically under 1 MB) and avoids cleanup logic.

- **Schema specified in prompt** — spelling out the exact field names, types, and structure inside the prompt removes the need for a response validation or transformation layer. Gemini consistently returns the correct shape when the schema is explicit.

- **String dates in deadlines** — deadlines are stored as `{ label, date }` string pairs rather than parsed `Date` objects. Notices frequently contain date expressions that cannot be reliably parsed into ISO dates ("last working day of the month", "before the next academic session begins"). Storing them as strings preserves Gemini's output without data loss.

- **Single checklist update endpoint** — instead of sending the full checklist array on every tick, the PUT endpoint accepts a single `{ index, done }` object and updates only that element in MongoDB using a computed field path. This keeps the payload minimal and avoids race conditions if a user ticks items quickly.

- **No user authentication** — the app is intentionally stateless on the user side. Any client with a notice `_id` can fetch or update that notice. This keeps the API simple and removes the need for session management, which is appropriate for a tool where the frontend stores history in localStorage rather than user accounts.

- **CORS built with filter(Boolean)** — the allowed origins array includes `process.env.FRONTEND_URL` which is undefined if the variable is not set. Filtering the array removes undefined values before passing it to the cors middleware, so a misconfigured environment does not silently block all production requests or add `undefined` as a literal origin.

## Setup

```bash
cd backend
npm install
cp .env.example .env
```

Edit `.env` and fill in your values, then:

```bash
npm run dev
```

The server starts on port 5000. You should see `DB Server connected` and `server listening on 5000` in the console.

## Deploying to Render

1. Push your code to GitHub (make sure `.env` is in `.gitignore`).
2. Create a new Web Service on [Render](https://render.com), connect your repo, and set the root directory to `backend/`.
3. Set the build command to `npm install` and the start command to `node server.js`.
4. Add your four environment variables in Render's dashboard: `PORT`, `DB_URL`, `GEMINI_API_KEY`, `FRONTEND_URL`.
5. Deploy. Render gives you a URL like `https://notice2action-api.onrender.com`.

Note: Render's free tier spins down after 15 minutes of inactivity. The first request after a cold start takes around 30 seconds.

## Common Issues

**`DB Server connected` never appears** — check your `DB_URL`. If using MongoDB Atlas, make sure your IP address is whitelisted in the Atlas network settings (or set `0.0.0.0/0` for development).

**Gemini returns a parsing error** — Gemini occasionally wraps JSON in a markdown code block. The backend strips this automatically. If you are still seeing parse errors, add a `console.log` to the raw Gemini response text to inspect what it is actually returning.

**CORS errors in the browser** — make sure `FRONTEND_URL` in your `.env` exactly matches the origin of your frontend including `http://` or `https://` and no trailing slash.

**PDF upload returns 400** — `pdf-parse` cannot read password-protected or image-only PDFs (scanned documents with no text layer). The notice must be a PDF with actual text content, not a scan.
